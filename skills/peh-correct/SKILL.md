# Prevent Recurring Mistakes

Write all engineering outputs in English. Read [scope.md](references/scope.md) before any writes, and [proof.md](references/proof.md) when selecting a constraint. This skill prevents recurrence; it is not an instruction to fix every review comment or run global formatting.

1. Ground the mistake in supplied corrections, actual regressions, reverts, or review evidence. Prefer a class with at least two occurrences; accept a single high-impact example when the user explicitly wants prevention. Limit the first pass to one class. Do not mine all repository history automatically.
2. Name the invariant and find the smallest useful enforcement point. Consider state ownership/architecture, types, a targeted lint/static check, and a behavioral regression test. Prefer the strongest proportionate constraint; a large architecture change is not automatically better than a small test. Reuse established tooling and avoid new dependencies unless necessary.
3. Prepare a concrete plan: evidence, proposed rule, allowed/bad examples, enforcement location, exact changed files, rollout scope, potential false positives, and validation. Inspect code and build the proposal before asking about scope. Do not edit shared files merely to make the proposal concrete.
4. Resolve write scope once. Honor explicit `local-only`, `project`, or `proposal` instructions, existing authorization, and any applicable team policy. If scope is unspecified, ask one focused question after the plan: “For [specific constraint], should I implement a personal local-only check, make the listed project changes, or leave a proposal?” Recommend local-only for a shared-tooling policy that the user does not manage. Prepare examples and checks while awaiting the decision; do not make dependent writes.
5. In local-only mode, use the external workspace identified by `scripts/local_workspace.py --repo REPO --create`. Put checks, config, proofs, and any disposable fixture copies there. Do not edit the target repository, even ignored files, .git/info/exclude, shared ESLint/Clippy config, package manifests, CI, AGENTS.md, or CLAUDE.md. Run against source read-only. If a constraint requires production types or architecture, provide that project proposal and implement only a useful local check that can honestly be supported. Explain that a personal check is opt-in and cannot enforce team CI.
6. In project mode, make only the authorized minimal changes using the team's established commands and conventions. Shared lint/CI policy, exported types, schema, dependency, and architecture changes need concrete authorization; a generic “correct this” is not blanket authorization. Explicit approval for the listed change is sufficient; do not ask repeatedly. Do not perform a sweeping autofix or unrelated cleanup.
7. Prove the constraint rejects the real bad case and accepts the smallest valid counterpart plus a relevant edge case. Use a disposable copy or fixture for the historical bad case rather than reverting the user's working tree. Run the established relevant checks on the final result, and report their limits.
8. Return one rule with evidence, scope, implementation, failing/passing proof, bypass/rollback, and whether wider adoption needs a team decision. Keep any instruction note short and pair it with what enforces it. Save an optional Obsidian note only on request.

In proposal mode, return the ready-to-implement rule and validation design without writes. Stop when the scoped rule is proved or its limit is explicit. Never automatically migrate a local-only rule into project configuration, post to GitHub, install a hook, push, or merge.
